# ТЗ: платформа анализа климатических трендов Кыргызстана

Nov 14, 2026 · @Alibek

## 1. Общие сведения

Платформа — веб-приложение с бэкендом, которое по открытым спутниковым данным показывает, что меняется в климате Кыргызстана, почему, где именно и насколько по-разному в разных регионах.

- **Контекст:** NASA Space Apps Challenge 2026 (14–15 ноября), челлендж Earth System Trend Detective.
- **Проблема:** данные разбросаны по десяткам сайтов и форматов; существующие сервисы показывают график, но не отвечают на вопрос «есть ли тренд и что он значит».
- **Решение:** единая нормализованная база, простой путь «раздел → место → параметр → период», статистический анализ тренда (Манн–Кендалл) и вывод простыми словами.
- **Отличие от аналогов:** готовый ответ вместо графика, цепочка связанных переменных, привязка глобальных явлений к конкретным объектам страны, сравнение регионов с противоположными трендами.
- **Язык интерфейса:** русский; кыргызский и английский — после MVP (тексты выносятся в словари сразу).

Обозначения приоритета в документе: **P0** — без этого нет демо, **P1** — основная ценность, **P2** — если останется время.

## 2. Пользователи и сценарии

Платформа рассчитана на человека без подготовки в климатологии: результат должен быть понятен без чтения документации.

| Пользователь | Что хочет | Что получает |
| --- | --- | --- |
| Студент, школьник | Понять, что происходит с озером или ледником | График, вывод простыми словами, цепочку причин |
| Журналист | Проверить утверждение цифрами | Тренд, значимость, скорость изменения, ссылку на источник данных |
| Сотрудник госоргана | Понять, какие районы в зоне риска | Сравнение регионов, карту объектов |
| Учёный, аналитик | Быстро получить очищенный ряд | Нормализованные данные, параметры теста, выгрузку CSV |

Ключевые сценарии:

1. **Анализ параметра.** Раздел «Вода» → Иссык-Куль → уровень воды → 2000–2025 → график, тренд, вывод, цепочка связанных переменных.
2. **От глобального к местному.** На карте выбрать «Глобальное потепление» → загораются объекты → клик по Токтогулу → местный график рядом с глобальным показателем.
3. **Сравнение.** Выбрать переменную «осадки» → платформа показывает два региона с противоположными трендами рядом.
4. **Произвольная точка.** Клик по карте → ряд по ближайшей ячейке сеточных данных → тот же анализ.

## 3. Границы MVP

В MVP данные загружаются в базу заранее пакетными скриптами, а не запрашиваются у NASA в момент клика пользователя: запросы AppEEARS асинхронные и могут выполняться долго, а Giovanni API отдаёт ряды только по одной точке.

**Входит:**

- Территория — только Кыргызстан; готовый каталог объектов (раздел 5) плюс произвольная точка по сеточным данным.
- Четыре раздела: вода, ледники и снег, климат, растительность.
- Шаг времени — месяц; годовые агрегаты считаются из месячных.
- Все шесть функций из раздела 9.
- Выгрузка ряда и результата анализа в CSV.

**Не входит:**

- Прогнозы и моделирование будущего.
- Регистрация, личные кабинеты, роли.
- Загрузка пользовательских данных.
- Наземные данные Кыргызгидромета (нет открытого API).
- Запросы к внешним API в реальном времени, суточный шаг, мобильное приложение.

Ограничения, которые влияют на архитектуру:

- Giovanni API не возвращает среднее по области — для регионов усредняем сеточные файлы сами.
- Прямых спутниковых рядов «масса ледника» и «расход реки» в этих источниках нет. Для ледников используем косвенные показатели (снежный покров и температура поверхности в границах ледника), для рек — модельный сток GLDAS по бассейну. В интерфейсе это подписывается явно.
- Точные идентификаторы наборов, версии и периоды сверяются с каталогами при настройке загрузчика; значения в таблице — ориентир.

## 6. Архитектура и стек

Система состоит из четырёх частей: загрузчик данных пишет в базу, бэкенд читает из базы и считает анализ, фронтенд общается только с бэкендом. Внешние API вызывает только загрузчик.

| Компонент | Ответственность | Предлагаемый стек |
| --- | --- | --- |
| Загрузчик (ETL) | Скачивание, нормализация, запись рядов, журнал загрузок | Python, earthaccess, xarray, pandas, geopandas |
| База данных | Каталог, ряды, кэш результатов анализа | PostgreSQL + PostGIS (на хакатоне допустим SQLite + GeoJSON-файлы) |
| Бэкенд (API) | Каталог, ряды, тренд, цепочка, карта, сравнение | Python, FastAPI, pymannkendall, scipy |
| Фронтенд | Экраны, карта, графики | React + TypeScript, MapLibre или Leaflet, Plotly или ECharts |
| Развёртывание | Один сервер или PaaS | Docker Compose: api, db, статика фронтенда |

Принципы:

- Python на бэкенде обязателен: готовые библиотеки для теста Манна–Кендалла и сеточных данных.
- Тяжёлые расчёты (тренды по всем объектам для функций 5 и 6) выполняются после загрузки и кэшируются; запрос пользователя по готовому объекту не должен запускать пересчёт.
- Секреты (токен Earthdata) — только в переменных окружения бэкенда.
- Стек — предложение; команда может заменить компоненты, сохранив контракты API из раздела 10.

## 7. Модель данных

Центральная сущность — ряд: одна переменная для одного объекта из одного набора данных. Всё остальное либо описывает ряд, либо посчитано из него.

| Таблица | Назначение | Ключевые поля |
| --- | --- | --- |
| `section` | Разделы интерфейса | code, name, order |
| `source` | Источник данных | code, name, url, license, citation |
| `variable` | Переменная | code, section, name, unit, yearly\_agg (mean/sum/max), season\_months, direction\_note |
| `object` | Объект или регион | code, type, name, geom (полигон), marker (точка), parent |
| `series` | Ряд = объект × переменная × источник | object, variable, source, dataset\_id, native\_step, date\_from, date\_to, is\_proxy |
| `observation` | Значение ряда | series, date (первое число месяца), value, quality (ok / filled / outlier) |
| `trend_result` | Кэш анализа | series, date\_from, date\_to, agg, trend, p\_value, tau, sen\_slope, intercept, n, method, computed\_at |
| `chain_template` | Шаблон цепочки для раздела | section, target\_variable, name |
| `chain_link` | Звено цепочки | template, order, variable, expected\_relation (+/−), explanation\_text |
| `phenomenon` | Глобальное явление | code, name, description, global\_series |
| `phenomenon_object` | Связь явления с объектом | phenomenon, object, local\_variable, weight, note |
| `ingest_run` | Журнал загрузок | source, started\_at, finished\_at, status, rows, error |

Правила:

- Глобальные показатели хранятся как обычные ряды объекта с типом `global`.
- В `observation` лежат уже нормализованные значения; сырые файлы хранятся отдельно на диске и в базу не попадают.
- `trend_result` уникален по (series, date\_from, date\_to, agg) и сбрасывается при новой загрузке ряда.

## 8. Пайплайн сбора и нормализации

Каждый источник подключается отдельным модулем-адаптером с общим интерфейсом `fetch → parse → normalize → load`; добавление источника не затрагивает остальные.

1. **Скачивание.** Адаптер получает сырые данные за весь доступный период по списку объектов из каталога. Повторный запуск докачивает только новые даты.
2. **Пространственная привязка.** Для сеточных данных — среднее по ячейкам внутри полигона объекта с весом по площади; для точки — ближайшая ячейка. Система координат — WGS84 (EPSG:4326).
3. **Единицы.** Приведение к единицам каталога: K → °C, кг/м²/с → мм/мес, доли → %. Коэффициенты описываются в конфигурации адаптера.
4. **Шаг времени.** Приведение к месяцу: суточные и 8/16-дневные данные усредняются или суммируются по правилу переменной; нерегулярные ряды альтиметрии — среднее за месяц.
5. **Контроль качества.** Отбрасываются значения с плохими флагами качества источника (облачность MODIS, большая ошибка альтиметрии). Выбросы — значения дальше 4 межквартильных размахов от медианы своего календарного месяца — помечаются `outlier` и исключаются из анализа.
6. **Пропуски.** Разрыв до 2 месяцев подряд заполняется линейной интерполяцией с пометкой `filled`; более длинные остаются пропусками. Год с менее чем 9 валидными месяцами (или менее 2/3 месяцев сезона) в годовой агрегат не попадает.
7. **Запись.** Загрузка в `observation` идемпотентна (upsert по series + date); итог записывается в `ingest_run`.
8. **Пересчёт.** После загрузки пересчитываются тренды по всем рядам за полный период и за стандартные окна; результаты кладутся в `trend_result`.

Требования к пайплайну:

- Запуск одной командой для одного источника или всех сразу.
- Сбой одного источника не останавливает остальные.
- Доля заполненных и отброшенных значений по каждому ряду доступна через API и показывается пользователю.

## 9. Функциональные требования

Шесть функций платформы расписаны как нумерованные требования; каждый номер — кандидат в отдельную задачу.

### Ф1. Единая база данных (P0)

- Ф1.1. Адаптеры для источников из раздела 4; минимум для демо — GLDAS, Hydroweb, NOAA.
- Ф1.2. Нормализация по правилам раздела 8.
- Ф1.3. Каталог разделов, объектов и переменных в базе, с геометрией объектов.
- Ф1.4. Для каждого ряда хранятся источник, набор данных, период, признак косвенного показателя, доля заполненных значений.
- Ф1.5. Журнал загрузок и команда повторной загрузки.

### Ф2. Интерфейс с разделами (P0)

- Ф2.1. Пошаговый выбор: раздел → место → параметр → период. Каждый следующий шаг показывает только варианты, для которых есть данные.
- Ф2.2. Место выбирается тремя способами: готовый объект из списка, регион, точка на карте.
- Ф2.3. Период по умолчанию — весь доступный; границы выбираются с точностью до года и не выходят за пределы данных.
- Ф2.4. Выбор сохраняется в адресе страницы, чтобы результатом можно было поделиться ссылкой.
- Ф2.5. Каждый термин (тренд, значимость, аномалия) имеет подсказку простыми словами.

### Ф3. Анализ тренда по Манну–Кендаллу (P0)

- Ф3.1. Анализ выполняется на годовых значениях (агрегация по правилу переменной), чтобы убрать сезонность. Минимум — 10 валидных лет; иначе ответ «недостаточно данных».
- Ф3.2. Считаются: статистика теста, тау Кендалла, p-значение, наклон Сена (скорость изменения в единицах в год) и его 95 % доверительный интервал.
- Ф3.3. При значимой автокорреляции первого порядка применяется модификация Хамеда–Рао; использованный метод указывается в результате. Метод один, без переключателей для пользователя.
- Ф3.4. Итог: «рост», «снижение» или «тренда нет» при уровне значимости 0,05; для p от 0,05 до 0,10 — формулировка «слабые признаки».
- Ф3.5. График: годовые значения, месячный ряд тонкой линией, линия тренда по Сену, пропуски и заполненные точки отмечены.
- Ф3.6. Вывод простыми словами собирается из шаблона. Пример: «Уровень озера за 2000–2025 годы снижается в среднем на 2 см в год. Тренд статистически значим: вероятность, что это случайность, меньше 5 %. За весь период изменение составило около 50 см».
- Ф3.7. Блок «Подробнее» с числами теста, методом, числом лет, долей пропусков и ссылкой на источник.
- Ф3.8. Выгрузка ряда и результата в CSV.

### Ф4. Цепочка связанных данных (P1)

- Ф4.1. Для каждого раздела задаются шаблоны цепочек в базе. Пример для уровня озера: температура воздуха → снегозапас и снежный покров → сток → испарение → уровень.
- Ф4.2. При анализе основного параметра бэкенд параллельно считает тренд по Ф3 для каждой переменной цепочки за тот же период и по той же территории (для озера — по его бассейну).
- Ф4.3. Для каждого звена считается ранговая корреляция Спирмена с соседним звеном по годовым значениям.
- Ф4.4. Звено получает статус: «подтверждается» (тренд значим и направление совпадает с ожидаемым), «не подтверждается», «нет данных».
- Ф4.5. Интерфейс показывает цепочку как ряд карточек со стрелками: переменная, направление и скорость тренда, статус, мини-график. Клик по карточке открывает полный анализ этой переменной.
- Ф4.6. Текст вывода формулируется осторожно: «согласуется с», «может объясняться». Цепочка показывает согласованность трендов, а не доказанную причинность; это указано в подсказке.

### Ф5. Связь глобальных процессов с местными (P1)

- Ф5.1. Главный экран — интерактивная карта Кыргызстана с объектами каталога.
- Ф5.2. Пользователь выбирает глобальное явление из списка; в MVP — «глобальное потепление», следующим — «изменение режима осадков».
- Ф5.3. На карте подсвечиваются объекты, связанные с явлением; размер или яркость точки отражает силу местного тренда (нормированный наклон Сена), незначимые тренды показаны приглушённо.
- Ф5.4. Клик по точке открывает панель: график местной переменной за выбранные годы, рядом или второй осью — глобальный показатель за те же годы, оба тренда и короткий текст связи.
- Ф5.5. Выбор периода действует на карту и панель одновременно.
- Ф5.6. Связи явление–объект–переменная и тексты пояснений хранятся в базе.

### Ф6. Сравнение регионов с противоположными трендами (P1)

- Ф6.1. Для выбранной переменной и периода бэкенд берёт готовые тренды по всем объектам одного типа.
- Ф6.2. Автоподбор пары: оба тренда значимы, знаки противоположны, максимальна разница нормированных наклонов. Если таких пар нет — показывается пара «самый быстрый тренд и самый стабильный объект» с честной подписью.
- Ф6.3. Экран сравнения: два графика рядом с общей шкалой времени, под каждым — вывод по Ф3, сверху — одно предложение о различии.
- Ф6.4. Пользователь может заменить любой объект пары вручную.
- Ф6.5. Список всех объектов с направлением тренда по выбранной переменной — таблица с сортировкой, для поиска районов риска.

## 10. API бэкенда

REST, JSON, префикс `/api/v1`; документация генерируется автоматически (OpenAPI). Контракты ниже фиксируются первыми, чтобы фронтенд и бэкенд шли параллельно.

| Метод и путь | Назначение | Основные параметры |
| --- | --- | --- |
| `GET /sections` | Разделы | — |
| `GET /objects` | Объекты с геометрией (GeoJSON) | section, type |
| `GET /variables` | Переменные, доступные для объекта | section, object |
| `GET /series` | Ряд значений и его метаданные | object или lat+lon, variable, from, to, agg (month/year) |
| `GET /trend` | Результат анализа по Ф3 с текстом вывода | object или lat+lon, variable, from, to |
| `GET /chain` | Цепочка по Ф4: звенья, тренды, статусы | object, variable, from, to |
| `GET /phenomena` | Глобальные явления | — |
| `GET /phenomena/{code}/map` | Объекты явления с силой местного тренда | from, to |
| `GET /phenomena/{code}/objects/{object}` | Местный и глобальный ряды, оба тренда, текст | from, to |
| `GET /compare/auto` | Автоподбор пары с противоположными трендами | variable, type, from, to |
| `GET /compare` | Сравнение двух заданных объектов | variable, a, b, from, to |
| `GET /trends` | Тренды всех объектов по переменной | variable, type, from, to |
| `GET /export.csv` | Выгрузка ряда и результата | как у `/trend` |
| `GET /health` | Состояние сервиса и дата последней загрузки | — |

Общие правила:

- Ошибки возвращаются в едином формате `{code, message}`; «недостаточно данных» — штатный ответ, а не ошибка сервера.
- Ответ `/trend` содержит поля: trend, p\_value, tau, sen\_slope, slope\_ci, unit, n\_years, method, missing\_share, summary\_text, source.

## 11. Экраны и интерфейс

В приложении четыре экрана; с любого можно перейти к полному анализу параметра.

| Экран | Содержание | Функции |
| --- | --- | --- |
| Главная (карта) | Карта Кыргызстана, выбор глобального явления, подсветка объектов, боковая панель с графиком объекта, ползунок периода | Ф5 |
| Исследовать | Пошаговый выбор «раздел → место → параметр → период», карта для выбора точки | Ф2 |
| Результат анализа | Вывод простыми словами сверху, график с линией тренда, блок «Подробнее», цепочка связанных переменных, кнопки «Сравнить» и «Скачать CSV» | Ф3, Ф4 |
| Сравнение | Выбор переменной, два графика рядом, таблица трендов по всем объектам | Ф6 |

Требования к интерфейсу:

- До результата — не более четырёх кликов с главного экрана.
- Направление тренда передаётся и цветом, и значком со словом; значимость — словами («уверенный», «слабый», «не выявлен»).
- Состояния каждого экрана: загрузка, нет данных, недостаточно данных для теста, ошибка сети.
- Косвенные показатели (модельный сток, снежный покров вместо массы ледника) помечены значком с пояснением.
- Под каждым графиком — источник данных и период.
- Адаптивная вёрстка: ноутбук и телефон; на телефоне графики сравнения идут друг под другом.

## 13. Критерии приёмки

MVP принят, когда все пункты ниже проходят на развёрнутом стенде.

- [ ] В базе есть ряды минимум из трёх источников, минимум для 8 объектов и 6 переменных, в единых единицах и с месячным шагом.
- [ ] Повторный запуск загрузчика не создаёт дублей.
- [ ] Путь «Вода → Иссык-Куль → уровень воды → период» проходится без подсказок и заканчивается графиком и выводом.
- [ ] Результат теста совпадает с эталонной реализацией (pymannkendall) на трёх контрольных рядах: возрастающем, убывающем, шумовом без тренда.
- [ ] Ряд короче 10 лет даёт ответ «недостаточно данных», а не тренд.
- [ ] Вывод содержит направление, скорость с единицами и значимость; числа в тексте равны числам в блоке «Подробнее».
- [ ] Для уровня Иссык-Куля показывается цепочка минимум из четырёх звеньев с трендом и статусом каждого.
- [ ] На карте при выборе «глобального потепления» подсвечиваются минимум 5 объектов; клик открывает местный график рядом с глобальным показателем.
- [ ] Экран сравнения сам предлагает пару объектов и показывает два графика рядом; пару можно изменить.
- [ ] Ссылка на результат открывает тот же результат в другом браузере.
- [ ] При отключённом доступе к внешним API все сценарии из раздела 2 по готовым объектам работают.
- [ ] Проект поднимается по README на чистой машине.

## 15. Риски и открытые вопросы

Главный риск — время на загрузку данных: она должна начаться раньше остальной разработки.

| Риск | Последствие | Что делаем |
| --- | --- | --- |
| Запросы AppEEARS выполняются долго | Нет данных MODIS к демо | Отправить задачи первыми; демо не зависит от MODIS |
| Сеточные файлы GLDAS за 25 лет — большой объём | Долгая загрузка | Брать месячный продукт и вырезку по Кыргызстану через OPeNDAP |
| Грубое разрешение 0,25° в горах | Ряды по небольшим объектам неточны | Для малых объектов использовать MODIS; подписывать разрешение в интерфейсе |
| Нет прямых рядов по массе ледников и расходу рек | Выводы по косвенным показателям | Явно маркировать; формулировки без утверждений о массе льда |
| Цепочку могут принять за доказанную причинность | Неверные выводы пользователей, вопросы жюри | Осторожные формулировки и статусы звеньев (Ф4.4, Ф4.6) |
| Короткие ряды (с 2000 г.) и природные циклы | Тренд зависит от выбранного периода | Показывать период в выводе; не экстраполировать |
| Разрыв GRACE 2017–2018 | Пропуск длиннее допустимого | Не заполнять; годы исключаются из теста |

- [ ] Какие объекты Кыргызстана реально есть в Hydroweb, кроме Иссык-Куля (Токтогул, Сон-Куль, Чатыр-Куль) — проверить на hydroweb.next.
- [ ] Какие наборы берём из NOAA и KNMI — сверить со списком во вкладке Resources челленджа.

## 16. Разделение на троих

ТЗ делится по слоям: один человек отвечает за данные, второй за бэкенд и анализ, третий за интерфейс. Каждая из функций 4–6 проходит через всех троих, поэтому стыки между частями описаны отдельно.

**Общий старт (все трое, первый час):** согласовать схему базы (раздел 7), контракты API (раздел 10) и коды объектов и переменных (раздел 5). После этого каждый работает независимо: фронтенд на заглушках, бэкенд на тестовых рядах, данные грузятся параллельно.

### Часть 1. Данные

Отвечает за то, чтобы в базе лежали чистые, нормализованные ряды по всем объектам. Разделы ТЗ: 4, 5, 8. Модули: М2, М3 и наполнение справочников для М7 и М8. Требования: Ф1.1–Ф1.5, содержимое для Ф4.1 и Ф5.6.

1. Получить доступ Earthdata Login и сразу отправить задачи AppEEARS по MODIS — они выполняются дольше всего.
2. Собрать геометрию объектов: контуры озёр, водохранилища, бассейнов Нарына и Чу, ледников, границы областей (М2).
3. Заполнить каталог: разделы, переменные с единицами и правилом годовой агрегации, объекты.
4. Написать адаптеры трёх базовых источников: GLDAS, Hydroweb, NOAA (М3, P0).
5. Реализовать нормализацию: единицы, месячный шаг, флаги качества, выбросы, пропуски (раздел 8).
6. Загрузить данные в базу, проверить отсутствие дублей при повторном запуске.
7. Заполнить справочники: шаблоны цепочек для каждого раздела с текстами пояснений; явление «глобальное потепление» и его связи с объектами.
8. По остатку времени: адаптеры IMERG, MODIS, GRACE, KNMI (P1).

- **Отдаёт бэкенду:** заполненные таблицы `section`, `variable`, `object`, `series`, `observation`, `chain_template`, `chain_link`, `phenomenon`, `phenomenon_object`.
- **Отдаёт фронтенду:** GeoJSON объектов и список кодов — в первые часы, до загрузки рядов.
- **Нужно от бэкенда:** схема базы и строка подключения.

### Часть 2. Бэкенд и анализ

Отвечает за каркас проекта, статистику и API. Разделы ТЗ: 6, 7, 10, 12. Модули: М1, М4, М5 и серверная часть М7, М8, М9. Требования: Ф3.1–Ф3.4, Ф3.6, Ф3.8, Ф4.2–Ф4.4, Ф4.6, Ф5.3 (расчёт силы тренда), Ф6.1–Ф6.2.

1. Поднять репозиторий, Docker Compose, базу со схемой из раздела 7 (М1).
2. Опубликовать описание API и заглушки ответов для фронтенда — до написания логики.
3. Реализовать модуль анализа: годовая агрегация, тест Манна–Кендалла с модификацией Хамеда–Рао, наклон Сена, проверка минимума в 10 лет (М4).
4. Написать генератор вывода простыми словами по шаблонам и тесты на трёх контрольных рядах.
5. Реализовать эндпоинты каталога, `/series`, `/trend`, `/export.csv` (М5) — после этого работает минимальное демо.
6. Пересчёт и кэш трендов по всем рядам после загрузки данных (`trend_result`).
7. Эндпоинты `/phenomena` с нормированной силой местного тренда (М8).
8. Подбор пар с противоположными трендами, `/compare`, `/trends` (М9).
9. Расчёт цепочки: тренды звеньев, корреляция Спирмена, статусы, `/chain` (М7).
10. Развёртывание стенда и README.

- **Отдаёт фронтенду:** заглушки API в начале, затем рабочие эндпоинты по одному, в порядке списка.
- **Отдаёт данным:** схему базы и команду запуска загрузчика в общем окружении.
- **Нужно от данных:** хотя бы один реальный ряд (уровень Иссык-Куля) как можно раньше для отладки.

### Часть 3. Фронтенд

Отвечает за все четыре экрана и за то, чтобы результат был понятен без подготовки. Разделы ТЗ: 2, 11. Модули: М6 и интерфейсная часть М7, М8, М9. Требования: Ф2.1–Ф2.5, Ф3.5, Ф3.7, Ф4.5, Ф5.1–Ф5.2, Ф5.4–Ф5.5, Ф6.3–Ф6.5.

1. Каркас приложения: маршруты четырёх экранов, словарь текстов, общие компоненты графика и карточки тренда.
2. Экран «Исследовать»: пошаговый выбор «раздел → место → параметр → период», выбор точки на карте, состояние в адресе страницы (М6).
3. Экран «Результат»: вывод сверху, график с линией тренда и отметками пропусков, блок «Подробнее», кнопка CSV (М6).
4. Состояния всех экранов: загрузка, нет данных, недостаточно данных, ошибка сети.
5. Главный экран: карта Кыргызстана, выбор явления, подсветка объектов, боковая панель с местным и глобальным графиком, ползунок периода (М8).
6. Экран «Сравнение»: два графика рядом с общей шкалой времени, замена объекта в паре, таблица трендов (М9).
7. Карточки цепочки со стрелками, статусами и мини-графиками на экране результата (М7).
8. Подсказки к терминам, значки косвенных показателей, подписи источников, вёрстка под телефон.
9. Скриншоты и запись демо для подачи проекта.

- **Нужно от бэкенда:** заглушки API в первый час, затем рабочие эндпоинты.
- **Нужно от данных:** GeoJSON объектов для карты.
- **Отдаёт команде:** собранную статику для развёртывания и материалы демо.
